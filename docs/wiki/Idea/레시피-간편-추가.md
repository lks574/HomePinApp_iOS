# 레시피 간편 추가 (입력 마찰 줄이기)

[[RecipeEditor]] 수동 입력의 마찰을 줄여 **레시피를 쉽게 추가**하는 방향 브레인스토밍.
[[AI-적용-후보]] §A-2(레시피 텍스트 → 구조화)를 구체화한다. **방향 회의 결과이며
결정/아키텍처가 아니다** — 착수 시 ADR + 화면/스키마 노트로 구체화한다.

## 문제 (현재 마찰)

[[RecipeEditor]] 수동 입력 = 제목 + 종류(cuisine) + 요리타입(dishType) + 인분 + 시간 +
요약 + **재료 여러 줄(이름·수량)** + **단계 여러 줄**. 필드가 많고 반복 입력이라 마찰이
크다. "쉽게"의 핵심은 이 다항목 입력을 **한 번에 채우는 것**.

## 핵심 프레임: 구조화 엔진 1개 + 입력 소스 N개

앱엔 이미 `NLParseViewModel → AddDraftResolver → 확인 드래프트([[DraftReview]],
screen-09)` 파이프라인이 있다(현재 [[Item]] 전용). 레시피는 여기에
**`@Generable ParsedRecipe` 스키마 한 벌**(제목·재료배열·단계배열·dishType·인분·시간)을
더하면 같은 패턴을 재사용한다. 그러면 **"텍스트 → 구조화된 레시피 드래프트 → 확인 후
저장"** 이 뼈대가 되고, 나머지는 모두 **"그 텍스트를 어디서 얻느냐"** 의 문제로 수렴한다.
네 가지 입력 소스(아래)가 전부 이 하나의 코어로 합류한다.

## 입력 소스 후보

| # | 소스 | 마찰 감소 | 구현 노력 | 온디바이스 적합성 |
| --- | --- | --- | --- | --- |
| 1 | **음성/타이핑 자연어** ("김치찌개, 돼지고기 200g, 김치 한 컵… 볶고 끓이고") | 중 | 낮음 (기존 STT·파서 재사용) | ◎ 완전 온디바이스 |
| 2 | **텍스트 덩어리 붙여넣기** (블로그·메신저·메모 복사) | 큼 | 낮음 (입력창 + 파서) | ◎ |
| 3 | **사진 OCR** (요리책·손글씨 메모·잡지 촬영) | 큼 | 중 (VisionKit 파이프라인 추가) | ◎ Vision 도 온디바이스 |
| 4 | **스크린샷 OCR** (웹/앱 레시피 캡처) | 큼 | 중 (3과 동일 경로) | ◎ |
| 5 | **공유 시트(Share Extension)** (사파리·메모에서 "공유 → HomePin") | 매우 큼 | 높음 (앱 익스텐션 타깃 신설) | ○ (텍스트면 ◎) |
| 6 | **URL 직접 가져오기** (웹 레시피 주소 fetch) | 큼 | 높음 + 리스크 | △ 네트워크 fetch + HTML 파싱 불안정 |

AI 없이 경량 보완책:
- **기존 레시피 복제 후 수정** — 비슷한 레시피가 많을 때 즉효, 거의 공짜 구현.
- **점진적 추가** — "제목만 빠르게 저장 → 나중에 재료·단계 채우기". 완성 강박 제거.

코어를 먼저 만들고 소스를 단계적으로 붙인다(코어가 생기면 각 소스가 싸진다).

| **1** | 텍스트 입력창 = **복붙 + 타이핑 + 음성** | 셋 다 같은 단일 텍스트 입력이라 한 번에. 기존 [[Capture]] STT·파서 인프라 재사용. 가장 싸고 즉효 |

## 핵심 통찰: 공유 시트가 URL 문제를 우아하게 푼다

URL 직접 가져오기(#6, 네트워크 fetch + HTML 파싱)는 **온디바이스·서버리스 원칙과 가장
멀고 불안정**하다. 그런데 사파리에서 레시피 페이지 → 공유 → HomePin 으로 보내면, 페이지
(리더) 텍스트를 받아 그대로 코어에 넣을 수 있다. 앱이 직접 URL 을 긁지 않아도 되므로
**#5(공유)와 #6(URL)이 하나로 합쳐진다.** → URL 직접 fetch 는 후순위로 두고 공유
시트로 대체하는 게 깔끔하다.

## 설계 포인트 (착수 시 검토)

- **확인 드래프트의 레시피 버전**: [[Item]] 은 단건/다건이었지만 레시피는 보통 한 번에
  1개(재료 N·단계 N). 확인 화면에서 재료/단계를 줄 단위로 쉽게 고치게 — 모델이 단계
  순서·수량을 가끔 틀리니 **"교정 친화적" UI** 가 중요. [[DraftReview]] 패턴 확장.
- **재료 grounding = 킬러 루프 연결**: 파싱한 재료를 기존 [[Item]] 에 매칭하면 레시피
  추가가 곧바로 "재고 대비 보유/부족" 판정과 [[ShoppingItem]](장보기)로 이어진다.
  레시피 추가가 단순 입력을 넘어 소비 루프에 꽂히는 지점.
- **dishType/cuisine**: 저장값은 기존 raw 키 분류에 매핑(현지화 표시값 아님 — i18n
  결정과 일관). [[Recipe]] 참조.
- **기기 게이팅**: Foundation Models 미지원 기기는 수동 [[RecipeEditor]] 폴백(기존 패턴).
- **부분 실패**: 재료는 잘 뽑아도 단계 순서를 틀릴 수 있음 → 확인 화면 교정으로 흡수.
