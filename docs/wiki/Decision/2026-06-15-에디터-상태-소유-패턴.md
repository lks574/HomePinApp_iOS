# 2026-06-15 에디터 화면의 상태 소유 패턴

추가/편집 에디터 화면에서 draft·저장 로직을 **View 가 직접 들지**, **얇은
`@Observable` 모델이 들지** 결정한다. 상태 관리 기본 원칙(View↔SwiftData 직결 +
얇은 모델 2케이스)은 [[2026-06-12-네비게이션-UI구조]]·`docs/architecture.md` 의
"상태 관리" 가 단일 기준이고, 이 노트는 그 원칙을 **에디터에 어떻게 적용하는지**를
구체화한다.

## 맥락 (문제)

`ItemEditorView` 가 UI 레이아웃 + draft `@State`(이름·수량·위치·유통기한·메모) +
파생값(`canSave` 등) + `save()`(create/edit 분기, `normalizedName` 동기화,
spot→area 일관성)를 **한 struct 에 모두** 들고 있었다. 화면 코드에 도메인 쓰기
규칙이 갇혀 재사용·테스트가 어렵고 View 가 비대했다(사용자 지적).

## 결정

에디터의 **상태 복잡도**로 가른다.

- **단일 필드 + 단순 insert/update** → **View↔SwiftData 직결 유지.** 별도 모델 금지.
  - 예: `PlaceEditorView`(장소 이름), `SpotEditorView`(세부위치 이름). 이름 하나
    `@State` + 저장 시 직접 insert/프로퍼티 변경.
- **다필드 draft + 다단계 쓰기 불변식** → **얇은 `@Observable` 모델**이 draft 와
  `save(into:)` 를 소유. View 는 레이아웃과 순수 UI 상태(focus·picker 시트
  표시)만 갖고 모델에 바인딩(`@Bindable`).
  - 예: `ItemEditorModel`(`Features/Items/ItemEditorModel.swift`). create/edit
    `Mode`, draft 7필드, `canSave`, `save(into: ModelContext)`(spot→area 불변식 +
    `normalizedName` 동기화) 소유. `ItemEditorView` 는 `@State private var model` +
    `@Bindable` 바인딩만.

이는 새 규칙이 아니라 기존 "얇은 `@Observable` 2케이스(① 비영속 draft ② 다단계 쓰기
불변식)" 의 적용이다. `ItemEditor` 가 두 케이스 모두에 해당한다.

## 근거

- **테스트 가능** — 저장 규칙이 plain 클래스라 후반 테스트 단계의 "모델 로직·상태
  전이" 대상이 된다(View struct 에 갇히면 불가). `docs/wiki/Decision` 테스트 정책 참고.
- **View 는 선언적 UI 로 회귀** — "무엇을 보여주나" 만 남고 "어떻게 저장하나" 는 모델로.
- **과설계 방지** — 단일 필드 에디터까지 모델을 두지 않는다(Place/Spot 직결 유지).

## 영향 / 관련

- 코드: `ItemEditorView`(바인딩 전용) + `ItemEditorModel`(신규). `ItemEditorRoute.mode`
  타입이 `ItemEditorModel.Mode` 로 이동.
- 직결 유지: [[PlaceEditor]] · [[SpotEditor]].
- 화면 노트 [[ItemEditor]] "상태 관리" 갱신.
- 후속: `CaptureSheet`(NL 파싱 결과 structured draft)도 다필드 draft 가 되면 동일
  패턴(`@Observable` 모델) 후보.
