# 2026-06-22 유통기한 로컬 알림 스케줄링

만료일이 있는 물건에 대해 임박 시 로컬 알림을 보내는 리텐션 기능(screen-23)의
스케줄링 모델·권한·서비스 경계를 확정한다. 순수 온디바이스(UserNotifications),
외부 의존성·계정 없음.

## 맥락

`Item.expiresAt` 는 시각 없는 날짜(`.date`)다. 임박 판정은 이미 `Item.daysUntilExpiry`
/`isExpiringSoon`(0~3일)/`dDayLabel`/`expiringSoonByExpiry` 가 단일 소스로 들고 있다.
iOS 는 앱당 보류 로컬 알림을 **64개**로 제한한다. 권한은 사용자 흐름을 막지 않아야
하고(거부·미결정에도 차단 없음), 시작 시 자동 요청은 피한다. `@MainActor` 타입 안
시스템 콜백 클로저는 격리 트랩이 있어 modern async API 를 써야 한다.

## 결정

- **스케줄링**: 만료일 있는 물건마다 **D-1·D-0 2회**, **오전 9시 고정**(로컬 TZ)에
  `UNCalendarNotificationTrigger`. `expiresAt` 가 시각 없는 날짜라 앱이 09:00 을 정한다.
  이미 지난 시각 슬롯은 skip. 미래 만료 물건을 **마감 빠른 순**으로 정렬해 트리거 시각
  기준 **64 슬롯**이 찰 때까지 등록(결정적).
- **재계산**: **전체 cancel-and-reschedule**(`removeAllPendingNotificationRequests` 후
  재등록). 진입점 = 앱 시작(`AppModel.start`), 물건 추가/편집/삭제 후(ItemEditor·
  CaptureSheet bulk insert·PlaceDetail 삭제). 식별자는 `expiry-<itemID>-d1`/`-d0` 로
  결정적이라 멱등.
- **권한**: **on-demand** — Settings 토글 ON 시에만 `requestAuthorization` 호출. 시작 시
  자동 요청 안 함. 토글 ON 인데 시스템 거부면 `@AppStorage` 토글은 사용자 의도로 유지,
  `UNAuthorizationStatus` 별도 안내 행("허용 안 됨 — 설정 열기")으로 분기. modern
  `requestAuthorization(options:) async`·`notificationSettings() async` 만 사용(콜백
  격리 트랩 회피).
- **서비스 경계**: 신규 `@MainActor @Observable ExpiryNotificationService`
  (`Features/Notifications/`). `AppRootView` 가 `@State` 로 소유 + `.environment` 주입,
  `AppModel.start(...)` 에서 병렬 합류 뒤 reschedule. 선례 `AdService`·
  `VersionGateService` 와 동일한 비영속 셸 서비스 패턴. SwiftData 영속화는 직결이라
  service 로 감싸지 않으나, UserNotifications 는 비영속 외부 side-effect 라 분리 대상이다
  (= `docs/architecture.md` 의 "알림 service 경계" 확정).
- **요청 빌더 분리**: `makeRequests(for:now:)` 를 `nonisolated static` 순수 함수로 둬
  시스템 접근 없이 입력만으로 결정(후반 테스트 단계 대상).
- **플랫폼**: iOS·macOS 공통(UserNotifications 양 플랫폼 지원). `Project.swift` 무변경
  (usage description 불필요, background mode 기존). 시스템 설정 deep link 만
  `UIApplication.openSettingsURLString`(iOS) / `x-apple.systempreferences`(macOS) 분기.

## 대안 / 폐기한 선택지

- **물건당 모든 D-3~D-0 등록** — 64 상한을 빠르게 소진하고 임박 신호가 과해진다. D-1·D-0
  2회로 임박 시점에 집중.
- **새 임박 임계값 도입** — 기각. `Item.isExpiringSoon`(0~3일) 단일 소스 유지, 알림은
  그 중 D-1·D-0 만 발사(임계값 재정의 아님).
- **증분 갱신(변경분만 add/remove)** — 멱등·정확성 비용이 커서 기각. 전체
  cancel-and-reschedule 가 단순하고 중복·누락이 없다.
- **시작 시 자동 권한 요청** — 첫 실행에서 맥락 없는 권한 팝업은 거부율이 높다. 토글
  ON 시 on-demand 요청으로 의도 있는 시점에 묻는다.
