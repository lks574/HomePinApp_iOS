# 2026-06-17 검색 랭킹·초성·편집거리 — 결과 정렬과 매칭 확장

> 중앙 검색([[Capture]], `[screen-16]`)의 결과 정렬(랭킹)·초성 검색·오타 근사 매칭을
> 외부 의존성 없이 유니코드 산술/자체 DP 로 구현한다.

## 맥락

기존 검색은 매칭/비매칭만 판정(Bool)하고 정렬은 `@Query` 의 이름순에 의존했다.
정확히 일치한 결과와 메모 한 귀퉁이만 걸린 결과가 같은 줄에 섞이고, 한글 초성
질의("ㅅㄱ")나 한 글자 오타("우우"→"우유")는 전혀 잡지 못했다.

## 결정

- **랭킹 정렬**(`Shared/Search/SearchRanking.swift`): `enum MatchTier`
  (exact<prefix<contains<choseong<fuzzy)로 매칭 품질을 등급화한다. 매칭 함수는
  Bool 대신 `SearchRank?`(tier + statusWeight)을 반환하고, 결과는 `compactMap` +
  `sorted`(tier → statusWeight → 이름순)로 정렬한다. 동점은 `@Query` 이름순이 안정
  정렬로 가른다. `statusWeight` 는 물건=임박 우선·위치없음 후순, 레시피=지금 가능·
  임박 재료 우선.
- **초성 검색**(`Shared/Search/Hangul.swift`): 완성형 음절(0xAC00~0xD7A3)을 초성
  인덱스(`(value-0xAC00)/588`)로 분해해 19초성 호환 자모로 바꾼다. 질의가 **전부**
  호환 자모 초성 자음(0x3131~0x314E)일 때만 초성 매칭을 활성화하고, 일반 텍스트
  질의는 기존 경로를 그대로 탄다(회귀 0). 초성 매칭은 최하위에 가까운 `.choseong`
  등급.
- **편집거리 fallback**(`Shared/Search/Levenshtein.swift`): 음절 단위 `Character`
  배열에 대한 2행 DP. 정상 매칭 결과가 **하나도 없을 때만**, 전체 물건에 토큰별
  편집거리 임계(길이≤3→1, 그 외 2) 이내 근사 매칭으로 `.fuzzy` 등급 폴백. 정상
  매칭이 있으면 작동하지 않는다.
- 위 모든 경로는 `hasConcreteSignal` 가드(불용어/조사만 남은 빈 토큰 질의가 전체
  카탈로그를 노출하지 못하게)와 `normalizedName` 단일 매칭키를 **우회하지 않는다**.
  fallback 도 `hasConcreteSignal=false` 면 작동하지 않는다.
- **외부 의존성 추가 없음**: 초성/편집거리는 유니코드 산술/자체 DP 로 직접 구현
  (`Project.swift dependencies` 유지).

## 대안 / 폐기한 선택지

- **항상 fuzzy 매칭** — 정상 결과에 노이즈가 섞인다. 결과 0일 때만 폴백으로 한정.
- **외부 검색 라이브러리** — 과한 무게·의존성. 개인 재고 규모엔 in-memory 정렬로 충분.
- **초성 자모 정밀 분해(중성·종성까지)** — 현 요구(초성 질의)엔 불필요. 편집거리도
  자모 단위 정밀화는 follow-up 으로 남긴다(현재는 음절 단위).
